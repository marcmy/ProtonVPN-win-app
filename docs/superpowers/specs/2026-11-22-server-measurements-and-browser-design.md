# Server measurements and Browse all servers

## What the current app does

The installed Windows client opens Browse all servers from the empty search view. It loads the catalogue without waiting for a scan, remembers the feature tab and ping threshold, and shows scan progress. In the P2P view I inspected, rows showed server IDs, ping and load. Several rows with the same 31 ms ping had different health-bar colors. The list itself gave no explanation and required reading server IDs to distinguish locations. The entry point looks like an external link but opens an internal list. Its XAML also removes it from tab navigation.

The service starts discovery with one ICMP echo per endpoint and sends a second only after a miss. The store pools those checks with ordinary four-echo runs. Discovery therefore contributes outcomes from a sample size that depends on whether the first probe replied. The same data path also turns some route, service and send errors into missed packets. After two failed ordinary runs the client currently synthesizes a four-sample “confirmed outage.” These outcomes feed both the percentage and the grade.

Ordinary checks are sequential, with up to 500 ms per echo and three 100 ms gaps. That is a nominal timeout path of 2.3 seconds, plus 50 ms for route settling and any queue, route, firewall and IPC overhead. Visible-row refinement currently waits for a scheduler tick and yields while discovery is running. Network invalidation marks the latest result stale, but the aggregation still reads existing history after a new result arrives.

## Recommended measurement model

**Keep the first reply fast.** Render the catalogue and saved ping values immediately. Run a full first pass across the active feature scope at the existing maximum of 32 active endpoint checks. Send the first echo with the current 500 ms deadline. Publish the first valid reply immediately with an **Estimate** indicator. Keep the current second-attempt behavior for discovery when the first echo times out. Show **No ICMP reply** once both valid attempts time out. A discovery attempt may establish reachability or provide a preliminary RTT. Its outcomes do not enter the loss denominator.

**Start a fixed four-echo check for the connected server, selected server and visible rows.** Set the count before sending. Space sends at approximately 0, 100, 200 and 300 ms, allowing a later send while an earlier reply is pending. Each has the same 500 ms observation window. Publish provisional ping on the first reply if the row has no fresh RTT. The nominal tail is 800 ms after the first send on a fully admitted run, or roughly 850 ms with the current route-settle wait. A reply may arrive much earlier. Queue pressure can defer a burst. Defer before scheduling or discard an incomplete run from aggregate statistics if the route changes, the burst is canceled, or an attempt cannot be classified. Keep completed results available while refreshing.

**Keep evidence and status distinct.** Store the time, probe mode, actual responder RTT and outcome for each attempt. Use explicit outcomes for reply, deadline elapsed, network unreachable, local/setup failure and cancellation. For a completed fixed check, a reply or an actual echo timeout supplies a known outcome. Other outcomes drive status and retry diagnostics. If Windows cannot establish whether an echo was sent, treat it as unavailable. Use a successful retry as new evidence, retaining any valid completed fixed run independently. Remove the synthetic outage and five-second wait from the first displayed result. Any diagnostic recheck can run later within the same budget and cooldown.

| Display | Rule |
| --- | --- |
| Ping | One reply gives an estimate. With at least three fixed-check replies in the rolling window, show their median. Keep the fresh estimate until fresh fixed-check data is usable. |
| Loss | For an endpoint that has responded in the current route context, show missed / sent in details as soon as one valid four-echo burst finishes. Publish a whole percentage in the list after at least 12 eligible probes across three time-separated bursts. Keep the count and time frame in details. |
| RTT variation | Show median absolute deviation of successful fixed-check RTTs in details after at least eight replies across multiple bursts. Keep latency outliers visible in the history. |
| Load | Read the latest catalogue load for the logical server. Label it as server load and keep it independent of probe results. |
| State | Show **Estimate**, **Sampling**, **Saved**, **No ICMP reply**, **Route unavailable** or **Maintenance**, as applicable. Persist prior measurements with their timestamp when useful. The latest failure or stale evaluation must remain visible beside historical values. |

Use the newest six completed fixed checks within ten minutes for the current estimate, or fewer checks as they arrive. Space recurring bursts for one endpoint by at least 15 seconds and retain the visible-row and connected refresh cadence of about one minute. A count of 12 is a publication threshold, not proof of a stable underlying rate. For example, show “0 of 24 missed” in details rather than calling the path loss-free. Close-spaced samples can be correlated, so avoid advertising a confidence interval that assumes independent trials. Explain that these are round-trip ICMP echo observations to the physical entry endpoint. ICMP can receive special treatment, and the method cannot determine tunnel, exit or application packet loss. [RFC 6673](https://www.rfc-editor.org/rfc/rfc6673.html).

### Scheduler, route identity and compatibility

- Deduplicate discovery and fixed-check work by canonical destination, verified egress context and probe parameters. Publish observations to every eligible logical row using that endpoint while preserving each row’s plan, location and load. Resolve the connected panel from the actual connected physical entry endpoint and keep it distinct from a catalogue candidate until the identity and route match.
- Use one admission queue and one owner for each in-flight endpoint. Keep the existing 32-endpoint ceiling and add a shared limit on in-flight echoes and sends per second. Reserve discovery throughput during full sweeps. Populate currently visible pings first, then visit the rest of the active feature scope in Proton-score order, including unknown or stale servers. Run passive refinement in spare capacity or after the pass. Connected and explicitly selected endpoints get the first refinement capacity. Permit concurrent refinement during an active sweep only when measured performance meets the latency and coverage gates below. A queued refinement never blocks a first-ping update.
- Keep a subscriber reference for shared work. A tab change or list close removes its queued interests. Cancel work with no consumers when supported and hold the route and permit until native sends have completed or cancellation has settled. Keep the existing endpoint-level exclusion and negative cooldown across views. A failed check still finishes its progress unit. Publish completed progress as “Ping checked X of Y,” independent of the number of replies received.
- Capture the verified IPv4 physical route and a generation ID. An adapter, gateway, address or relevant route change keeps the previous snapshot available as **Saved** but starts a clean live window. Discard late results from the old generation and prevent an old worker from overwriting a new snapshot. Retain version 1 cached RTTs as historical only. Start the new loss and variation windows from versioned, qualified observations.
- Keep telemetry off the connection-selection path. Retain destination-specific route leases, cleanup ownership and existing exclusions. Before increasing work on the privileged service path, verify catalogue destination authorization before creating any permit or route. The current documentation describes catalogue validation, while the checked-out VPN controller and probe service show a direct address handoff and an IPv4 parse. Treat that discrepancy as an implementation verification item. Keep route verification as a condition for any direct-result label and avoid broadening firewall permits.
- Add negotiated or versioned probe results. Keep legacy IPC clients functional and render their RTTs as estimates where needed. Do not infer sample provenance from counts in legacy replies. Candidate service code can use the .NET 10 cancellation-aware async echo API, with Windows tests for actual cancellation and handle cleanup. [Microsoft Ping.SendPingAsync](https://learn.microsoft.com/dotnet/api/system.net.networkinformation.ping.sendpingasync?view=net-10.0).

### Alternatives

Four probes for every server during discovery would produce more early samples at the cost of scan throughput. Extending only the existing rolling average would smooth display values while still pooling discovery and measurement outcomes. The proposed scheduler decouples first-ping speed and full-catalogue coverage from the detail work where users are actively comparing servers.

## Browse all servers

Make **Browse all servers** a first-class action in the sidebar with a clear Back path. Open a dedicated, resizable WinUI content pane. On wide windows it uses the map’s content area while browsing. On compact windows the same view fills available space and details replace the list until Back. Preserve the return location, selection and scroll anchor. Preserve the VPN connection when opening or closing the browser.

- **Header.** Use “Browse all servers,” then the All, Secure Core, P2P and Tor tabs. Keep an in-page search for country, city or server ID. Typing narrows the current scope without switching modes. Use the existing feature, plan and exclusion rules. Do not expose private gateway locations outside their authorized catalogue.
- **Toolbar.** Show named **Sort** and **Max ping** controls and a compact results/progress line. Default to Proton’s existing recommended order, with Fastest ping, Lowest loss, Lowest load and Location alternatives. Lower is better for the measurement sorts. Unknown and saved values go after current comparable measurements. For a low-loss sort, use only published current ratios and break exact ties by larger sample count, then ping, then a stable server ID. Under a max-ping limit, use first-reply estimates as soon as they arrive. Put servers without current ping in a visibly labeled pending or unavailable section and keep them selectable where eligible. Expose a one-action filter reset in the empty state.
- **List.** Use a virtualized list with a sticky column header. Show flag and city/country plus server ID on two lines, and right-align **Ping**, **Loss** and **Load**. Put **Connected** and **Maintenance** beside the row identity. On compact windows keep location and Ping in the list and put Loss and Load in the selected-server details. Reuse localized flags, labels, accessibility resources and connection commands. Secure Core shows exit location plus the entry location and identifies the measured leg in details.
- **Details.** A click or Enter on a row selects it and opens details without changing the VPN connection. Show the route, time checked, sample counts, RTT variation and a short history with gaps for missing measurements. Expose an explicit **Connect** or **Switch server** action. Use a textual state label and a distinct focus treatment so meaning never depends on color or hover.
- **Updates.** Build lightweight rows once per catalogue change and bind telemetry only to affected rows. Coalesce status updates to about the existing 200 ms cadence. Keep scroll and keyboard focus anchored by server ID. In live sorts, defer reordering while the user is scrolling, navigating or operating a row, then apply the pending order on idle. Announce the resulting count and completion through accessible status text without announcing every packet. Match the app’s light, dark and high-contrast colors and test localization, text scaling and keyboard-only use.

## Release gates

Use a replay harness with identical endpoint sequences for the existing and proposed systems. Include warm and cold caches, 1,000 and 10,000 logical servers, shared IPs, quiet and bursty loss, high RTT, blocked ICMP, invalid routes and cancelled work. Benchmark the installed build and candidate on the same Windows host, alternating runs and reporting coverage, not only timing. Repeat live checks with the VPN connected and disconnected and with a physical network handoff.

1. **No speed regression.** Compare p50 and p95 catalogue paint, time to first visible fresh ping, and time to 90% and 100% first-pass coverage for the same active scope. The candidate must stay within baseline measurement noise with matching endpoints, deadlines and outcome coverage. Measure a warm-cache reopening independently.
2. **Faster useful detail.** Compare time to the first valid fixed check for the connected and selected server, including queue time, and time to 12 eligible probes for continuously visible candidates. Verify that a slow or failed send does not serialize the other three, and validate the nominal 800 ms send window under admitted, uncongested conditions.
3. **Accurate accounting.** Replay exact known RTTs and timeouts. Check that only completed fixed checks with classified outcomes drive loss, no send creates no loss, all-timeout endpoints report no reply, and no data crosses network generations. Verify shared endpoints, fallback attempts, skipped probes, repeated timeouts, retry, cache migration and mixed-version IPC.
4. **Smooth list.** Measure scroll and input responsiveness under a result burst, compare UI-thread time with the baseline, and verify focus and scroll anchors survive filtering and sorting. Test narrow widths, high contrast, scaling, keyboard traversal, feature isolation, restricted/maintenance rows and explicit connect behavior.

The timing figures above are derived from source constants and the proposed schedule. Live baseline performance, Windows cancellation behavior and the candidate measurement times remain to be verified during implementation.
